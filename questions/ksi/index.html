A KSI is met when three things are true. The measure fits the KSI. The measure works. Someone outside the provider has checked both. Our reviewers test each link.

- Security assertion: what the provider says is true. - Security measure: the thing they do or track that makes it true. - Evidence of implementation: proof the measure exists. Example: a config export. - Evidence of effectiveness: proof it works over time. Example: logs or metrics. - Verification: is this the right measure, and is it enough to show the KSI? Is the automation right? - Validation: is the measure in place and working? - Independent verification and validation (IV&V): a party outside the provider does both checks. The provider then answers its comments.

For each KSI we ask five things. Does the SDR entry cover each SDR-CSX-KSI item? Does the measure fit the boundary? Is the proof current for the stated cycle? Do the JSON and text agree? Did IV&V find the same thing?

We treat a KSI as demonstrated only when the chain from claim to independent check is complete. Our reviewers organize around the following terms: • Assertion: the provider's claim of a security outcome. • Measure: the objective, repeatable metric or method used to evaluate that outcome. • Evidence of implementation: artifacts showing the capability exists as described (configurations, policies, IaC). • Evidence of effectiveness: data showing the KSI operates as intended over time, not at a single point. • Verification: confirming the implementation matches the documented design (built right). • Validation: confirming the implementation achieves the intended outcome in operations. • IV&V: verification and validation by a FedRAMP Recognized assessor independent of the provider, reviewed at a technical level rather than from documentation or screenshots alone.

A KSI is adequate when the assertion is specific to the boundary, the measure is defined, implementation and effectiveness evidence are current and traceable, and automated validation results agree with the evidence. A KSI passing automated validation alone is not proof. We seek to document where automation stops and engineering judgment begins.

An example of our approach using just-in-time privileged access (KSI-IAM-JIT): • Assertion: no human holds standing admin access to production. • Measure: count of identities with persistent admin rights; target zero, checked daily. • Implementation: IdP group mappings, cloud IAM policies, and JIT elevation configuration. • Effectiveness: daily metric history and elevation logs showing time-bound grants that expired, with zero persistent assignments. • Verification: automated policy query confirms deployed roles match the design stated in the SDR. • Validation: a test elevation confirms access is granted, scoped, logged, and revoked on expiry. • IV&V: the assessor re-runs the query and samples log records against the daily measure; our reviewers confirm the SDR reflects that work and spot-check it with Government-approved tools.

If a provider submits only the policy export, we record implementation without effectiveness and issue a question, not an acceptance.

We apply this model today, dual-tagging a SaaS provider's Rev. 5 evidence to KSIs, and are scoping KSI evidence plans for a 20x Class B candidate.

CyberStorm Defense personnel evaluate Key Security Indicators (KSIs) by translating high-level security claims into immutable technical artifacts and empirical test outputs.
