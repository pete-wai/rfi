A KSI is met when three things are true. The measure fits the KSI. The measure works. Someone outside the provider has checked both. Our reviewers test each link.

- Security assertion: what the provider says is true. - Security measure: the thing they do or track that makes it true. - Evidence of implementation: proof the measure exists. Example: a config export. - Evidence of effectiveness: proof it works over time. Example: logs or metrics. - Verification: is this the right measure, and is it enough to show the KSI? Is the automation right? - Validation: is the measure in place and working? - Independent verification and validation (IV&V): a party outside the provider does both checks. The provider then answers its comments.

For each KSI we ask five things. Does the SDR entry cover each SDR-CSX-KSI item? Does the measure fit the boundary? Is the proof current for the stated cycle? Do the JSON and text agree? Did IV&V find the same thing?

Example: KSI-IAM-APM (Adopting Passwordless Methods). - Assertion: "All users sign in with phishing-resistant MFA." - Measure: a sign-in rule that requires FIDO2 or PIV. Plus a daily count of accounts that lack one. - Proof it exists: the rule export. It applies to all user groups. - Proof it works: 30 days of sign-in logs. Every login used FIDO2 or PIV. - Verification: does the rule cover admin consoles, break-glass accounts, and every tenant? Does the daily count pull from the real user list? - Validation: the count matches a sample we pull from the logs. A test login with a password gets blocked. - IV&V: the 3PAO ran the same checks. Its comments are closed.

Now say the rule is right, but 3% of logins still use passwords through an old app. The measure exists, but it does not fully work. We raise a question. We log it in the review sheet and tie it to the log data.

We treat a KSI as demonstrated only when the chain from claim to independent check is complete. Our reviewers organize around the following terms: • Assertion: the provider's claim of a security outcome. • Measure: the objective, repeatable metric or method used to evaluate that outcome. • Evidence of implementation: artifacts showing the capability exists as described (configurations, policies, IaC). • Evidence of effectiveness: data showing the KSI operates as intended over time, not at a single point. • Verification: confirming the implementation matches the documented design (built right). • Validation: confirming the implementation achieves the intended outcome in operations. • IV&V: verification and validation by a FedRAMP Recognized assessor independent of the provider, reviewed at a technical level rather than from documentation or screenshots alone.

A KSI is adequate when the assertion is specific to the boundary, the measure is defined, implementation and effectiveness evidence are current and traceable, and automated validation results agree with the evidence. A KSI passing automated validation alone is not proof. We seek to document where automation stops and engineering judgment begins.

An example of our approach using just-in-time privileged access (KSI-IAM-JIT): • Assertion: no human holds standing admin access to production. • Measure: count of identities with persistent admin rights; target zero, checked daily. • Implementation: IdP group mappings, cloud IAM policies, and JIT elevation configuration. • Effectiveness: daily metric history and elevation logs showing time-bound grants that expired, with zero persistent assignments. • Verification: automated policy query confirms deployed roles match the design stated in the SDR. • Validation: a test elevation confirms access is granted, scoped, logged, and revoked on expiry. • IV&V: the assessor re-runs the query and samples log records against the daily measure; our reviewers confirm the SDR reflects that work and spot-check it with Government-approved tools.

If a provider submits only the policy export, we record implementation without effectiveness and issue a question, not an acceptance.

We apply this model today, dual-tagging a SaaS provider's Rev. 5 evidence to KSIs, and are scoping KSI evidence plans for a 20x Class B candidate.

A security assertion is an unsubstantiated provider claim that a control or capability exists, such as stating that multi-factor authentication is enabled. A security measure is the specific technical or procedural mechanism implemented to satisfy a security requirement, such as an MFA policy or configuration standard. Evidence of implementation is documentation or artifact demonstrating the measure has been deployed, such as a screenshot, configuration export, or system security plan control implementation summary. Verification confirms that the evidence of implementation is accurate, complete, and consistent with stated configurations. CyberStorm Defense personnel evaluate Key Security Indicators (KSIs) by translating high-level security claims into immutable technical artifacts and empirical test outputs.

Definitions & Distinctions:

Security Assertion: A provider's qualitative claim that a security control requirement is satisfied (e.g., "All stored data is encrypted at rest").

Security Measure: The specific technical or operational mechanism deployed to fulfill the assertion (e.g., configuring AWS Key Management Service with customer-managed AES-256 keys).

Evidence of Implementation: Static or structural artifacts proving the security measure exists and is configured correctly (e.g., Terraform configuration files, architecture boundary diagrams).

Evidence of Effectiveness: Dynamic, empirical test data proving the security measure functions successfully under operational conditions (e.g., automated scan results, runtime logs, cryptographic validation tests).

Verification: Internal evaluation confirming that a security measure meets specified design, configuration, and engineering specifications.

Validation: Objective confirmation that the implemented security measure fulfills its intended operational purpose within the defined system authorization boundary.

Independent Verification and Validation (IV&V): Unbiased, third-party technical assessment conducted by an independent engineering team (such as CSD) that independently re-tests, inspects, and certifies both verification and validation without conflict of interest.

Concise Application Example (Encryption at Rest): A CSP makes a security assertion that databases are secure. They deploy AWS KMS AES-256 as their security measure. CSD inspects Terraform scripts and configuration exports as evidence of implementation, then reviews automated runtime execution logs and active key-rotation telemetry as evidence of effectiveness. Internal engineering teams perform verification of the configuration, vulnerability scans provide validation against NIST SP 800-53 controls, and CSD's independent assessment team conducts IV&V by executing direct API probes and storage volume inspections to certify the control's integrity
